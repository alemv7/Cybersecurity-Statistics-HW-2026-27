02Role of each standard

ComponentYearRoleType
BIP-392013Mnemonic (12-24 words from entropy + checksum) → 512-bit seed via PBKDF2-HMAC-SHA512 (2048 iterations, salt "mnemonic"+passphrase).generation + encoding + stretching
BIP-322012Derives master key and chain code (HMAC-SHA512) from the seed and constructs a tree of deterministic child keys (hardened and non-hardened).derivation
BIP-442014Path convention m/44'/coin'/account'/change/index. For Ethereum coin = 60, hence m/44'/60'/0'/0/i.convention

Keccak-2562012 (SHA-3 selection)Hash of the 64 bytes (x‖y) of the public key: the trailing 20 bytes form the address.hash
EIP-552016Uppercase/lowercase casing determined by the bits of Keccak-256 of the lowercase hex address: detects typos without changing the address value.checksum (encoding)

Key distinctions

  • Generation vs derivation: initial entropy is generated (randomness). Seed and child keys are derived deterministically: identical mnemonic yields identical addresses.
  • Public key: pair k ↔ Q = kG, practically non-invertible; enables signatures without revealing k.
  • Hash: unkeyed, deterministic compression, resistant to preimage and collision attacks; used here to compress and "obfuscate" the public key.
  • Checksum: minimal redundant information designed to detect errors, not to secure. In EIP-55 it is encoded within capitalization; in BIP-39 it constitutes the final bits of the last word.
  • Encoding: reversible representation without secrets (hex, BIP-39 wordlist, casing). It does not provide cryptographic security.

03Historical context

1977 RSA, first widely adopted public-key scheme.
2000 Standardisation of secp256k1 (SEC 2), later adopted by Bitcoin (2009).
2001 SHA-2 / SHA-512 (NIST FIPS 180-2); SHA-512 is used in BIP-32 and BIP-39.
2012 BIP-32 (hierarchical deterministic wallets); NIST selects Keccak for SHA-3.
2013 BIP-39 (mnemonics for deterministic wallets).
2014 BIP-44 (multi-account and multi-coin).
2015 SHA-3 standardized (FIPS 202); Ethereum launches with the original Keccak.
2016 EIP-55 (mixed-case checksum).

SHA-2 / SHA-512 vs Keccak / SHA-3

SHA-2 is based on the Merkle-Damgård construction with a compression function; Keccak uses a sponge construction (Keccak-f[1600] permutation, rate 1088 bits, capacity 512 for the 256-bit variants). They are completely distinct families, not direct evolutions of one another. Ethereum uses Keccak-256 (2012-2015), not the standardized SHA3-256: FIPS 202 introduced the domain separation suffix 01 before padding, resulting in a padding byte of 0x06 instead of 0x01. Same underlying permutation, distinct outputs.

04Why multiple primitives instead of a single one

  • BIP-39 / 32 / 44 manage keys: a single backup (easy-to-record words) for infinitely many accounts, deterministically and interoperably across wallet software.
  • secp256k1 provides the private/public relationship and digital signatures: a hash function cannot produce signatures, and a public key cannot be deduced from a private key via hashing.
  • Keccak-256 compresses and "obfuscates" the public key into 20 bytes; without hashing, the address would span 64 bytes.
  • EIP-55 provides error detection at zero byte overhead, fully backward-compatible with the legacy lowercase format.

Each primitive fulfills a different requirement: PBKDF2 must be intentionally slow, HMAC-SHA512 must act as a PRF, ECC must possess algebraic structure, and Keccak must completely destroy algebraic structure. No single algorithm can satisfy every need; separating roles also limits the blast radius should any primitive be broken (defense in depth).

05Statistical properties

Analysis on the test mnemonic: Keccak-256 avalanche effect (300 pairs of messages differing by 1 bit) and uniformity across 100 consecutive addresses m/44'/60'/0'/0/0…99.

Expected interpretation: the avalanche effect of a cryptographic hash changes an average of 128 out of 256 bits (σ = 8). Addresses are Keccak outputs of pseudorandom public keys, making bits and hex digits ≈ uniform and uncorrelated with the index, even though consecutive private keys are bound by HMAC rather than a linear relation. Uniformity is a property of the hash function; the hardness of inversion is instead provided by secp256k1.
